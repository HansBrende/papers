MAIN CONCLUSION
Consolidation is not the only available improvement. There are two accidental
source dependencies and one small compatibility boundary that can keep full
Mathlib out of a substantial native-computation subgraph without changing the
original sibling paper or any original public theorem statement. The bounded
proposal preserves original import paths as compatibility wrappers.

WHY THE NATIVE BRIDGE MATTERS
NativeMicrocode imported Transpose.Tape.Run only for Impl.next, a one-line
optional-step totalization. Run imports Defs, and Defs imports all Mathlib.
NativeMicrocode's other imports do NOT independently pull full Mathlib:
AbsoluteTape uses core-only Statement plus Mathlib's Turing tape; Microcode
uses CopyMachine/OperationalTrace. Their broad Mathlib.Tactic imports are
large but smaller than all Mathlib.
Merely deleting Run would be invalid: NativeMicrocodeRun has native_run and
native_trajectory, and FiniteProgramEncoding has a trajectory bridge. The
latter would reintroduce the heavy import through NativeZipper if not split.
The seven-core proposal explicitly handles all of these points.

combinations. It includes local, protected original, and pinned Mathlib

EXACT LEAN 4.34.1 / LAKE CACHE BEHAVIOR
Inspected installed source under:
/Users/hansbrende/.elan/toolchains/leanprover--lean4---v4.34.1/src/lean/

lake/Lake/Build/Module.lean:
- ModuleImportInfo.addImport (~309-380): a legacy importer mixes the imported
  legacyTransTrace plus allArtsTrace into its dependency trace. An import-all
  module similarly tracks all transitive/private artifacts. An ordinary
  new-module import uses public traces/artifacts instead.
- computeExportInfo (~477-522): legacy files have one full .olean artifact.
  A new module separates public .olean, .olean.server, .olean.private,
  .ir.sig and .ir. The ordinary public compile dependency hash uses .olean;
  meta/import-all paths deliberately track richer information.
- recFetchPreSetup (~590-613): dependency trace, source, options, module name,
  package identity and compiler arguments all feed the build trace.
  Therefore source edits require normal Lake invalidation. No timestamps,
  handcrafted traces, or fake caches should be used to suppress it.

Lean/Environment.lean:
- importModulesCore (~2112 onward): a new `module` cannot import a legacy
  non-module. With the module system disabled at the root, Lean imports all
  transitively referenced modules and ignores public/private annotations.
- mkModuleData/writeModule (~1858-1918): new modules retain full checked
  constants in .olean.private, while exported views can be smaller.

Consequences:
1. A facade that merely imports the original Run module cannot hide its full
   Mathlib closure from our legacy clients. Lean has no selective import of
   a few declarations from that existing legacy artifact.
2. Adding `module` only to native files is not a local drop-in fix: they need
   the protected legacy Transpose.Statement. A wrapper around Statement is
   still unable to import it from the new module system. This route would
   require a coordinated upstream migration, outside this bounded change.
3. If a later permitted module-system migration is considered, proof-only
   edits CAN in principle avoid invalidating ordinary public consumers when
   the exported artifact is unchanged. That is not the behavior of our
   present legacy files and is not promised without an actual A/B test.
4. `import all` or a legacy consumer deliberately restores private data and
   those dependency costs; mass conversion followed by import-all everywhere
   would undo much of the intended cache benefit.

PROOF RETENTION / AUDIT DETAIL
Lean/AddDecl.lean (~110-126) exports ordinary new-module theorem signatures
without their proof bodies; this is standard compiler behavior, not a new
source axiom. Full checked bodies remain in .olean.private. The installed
Lean/Util/CollectAxioms.lean (~112-154) computes an exported axiom-dependency
extension from full bodies and downstream #print axioms uses that metadata.
Thus new-module adoption would need a deliberate proof-retention audit and
full-data kernel replay path, not merely counting apparent public constants.
No module-system migration or signature-only stub is proposed for this pass.
